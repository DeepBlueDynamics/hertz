Solid project idea — and very buildable in Rust today. I dug through the current crate ecosystem, driver options, reference architectures, and the DSP details for squelch and scanning. Here's the full picture.

## Hardware and band realities

An RTL-SDR is the natural starting point (receive-only, ~$30–40). Two things matter for your specific bands. First, bandwidth: an RTL-SDR tunes 500 kHz–1.766 GHz with up to 3.2 MHz of instantaneous bandwidth, of which about 2.4 MHz is stable. That number is the key architectural fact: the entire 40-channel CB band (26.965–27.405 MHz) is only 440 kHz wide, so one capture sees every CB channel simultaneously — no retuning needed. VHF targets are more spread out (marine spans ~6 MHz, the 2m ham band 4 MHz), so there you either hop or pick a 2.4 MHz slice.

Second, the 27 MHz wrinkle. Most RTL-SDR dongles tune down to about 24–25 MHz, so CB is reachable without an upconverter, though strong FM broadcast interference often makes a filter or upconverter worthwhile. On the current RTL-SDR Blog V4 specifically, the input is triplexed into HF (0–28 MHz), VHF (28–250 MHz), and UHF bands, and everything below 28.8 MHz goes through a built-in upconverter handled transparently by the driver — you just tune 0–28.8 MHz normally. So CB rides the V4's HF path with proper gain control, which is a real improvement over the V3 for this use case.

Band cheat sheet for what you're scanning:

| Band | Range | Mode | Notes |
|---|---|---|---|
| CB | 26.965–27.405 MHz | AM + SSB (FM legal since 2021) | 40 ch, 10 kHz spacing; ch 19 truckers, ch 9 emergency; SSB clusters on 36–40 |
| 2m amateur | 144–148 MHz | NBFM (±5 kHz dev) | CTCSS common on repeaters |
| MURS | 151.82–154.60 MHz | NBFM | 5 channels |
| Marine VHF | 156–162.025 MHz | NBFM | 25 kHz channels, ch 16 = 156.800 |
| NOAA weather | 162.40–162.55 MHz | NBFM | Continuous carrier — breaks naive auto-squelch |
| Air band | 118–137 MHz | AM | If you ever extend to it |

The mode mix matters: your demod stage needs at least NBFM and AM, plus SSB if you want the interesting half of CB.

## The Rust ecosystem: three viable routes

**Route 1 — FutureSDR.** The most ambitious framework: an async SDR runtime that runs on Linux, Windows, macOS, Android, and in the browser via WASM, with flowgraph blocks and pluggable schedulers. It's actively developed — a major runtime overhaul recently landed that cleaned up the internals while leaving the flowgraph-building API mostly untouched — but it's still pre-1.0 (crates.io shows 0.0.x versioning), and the project itself recommends cloning the repo and building your app inside it rather than adding it as an external dependency, since applications often require runtime changes. Its hardware layer is `seify`, a Rust SDR hardware abstraction that wraps SoapySDR (so it supports basically every frontend) while providing a migration path toward pure-Rust drivers using rusb/WebUSB.

**Route 2 — rustradio.** Thomas Habets' framework is a GNU Radio-inspired crate where blocks connect via typed streams into a graph, with a library including FFT filters and sources, and optional features for librtlsdr and SoapySDR backends. It's smaller and simpler than FutureSDR, actively maintained, and easy to depend on as a normal crate.

**Route 3 — roll your own on a driver crate.** Honestly the best fit for a focused scanner, because your pipeline is fixed and simple. Driver options: `rtl-sdr-rs`, a Rust port of the Osmocom librtlsdr including the RTL-SDR Blog fork's modifications (needed for V4 support), which talks USB directly — on Linux you blacklist the DVB-T kernel modules; `librtlsdr-rs`, a newer pure-Rust port with no C dependency that covers all five tuner families (R820T/R828D, E4000, FC0012/13, FC2580) and offers async streaming; or the `soapysdr` bindings crate, which abstracts over RTL-SDR, HackRF, Airspy, SDRplay and more via the system SoapySDR library if you want hardware portability. For DSP: `rustfft` for spectrum, the `sdr` crate for fast FIR and CIC filtering/decimation, `num-complex` for IQ math, `hound` for WAV writing, and `cpal` for live audio out.

## Prior art worth stealing from

Three Rust projects and two C/Python classics map almost exactly onto your feature list. **sdrrat** is a Rust terminal SDR receiver whose architecture doc is basically a blueprint: a UI thread and a DSP thread communicating over crossbeam channels, with the DSP thread wrapping a FutureSDR flowgraph — a seify/SoapySDR source fanning out to an FFT spectrum path and a demod path that decimates to ~32 kHz, dispatches between an FM discriminator and an AM envelope detector via an atomic, and feeds a power meter whose value the squelch reads. **Rigflow** is an open-source Rust client/server SDR app where a lightweight server owns the radio and DSP (RTL-SDR supported, including direct-sampling HF) and offers NFM, AM, SSB, squelch, and IQ recording. **NyxScope** (Rust/Tauri) is notable for its squelch design: adaptive auto-squelch with a one-shot calibration pass plus continuous noise-floor tracking, and a multi-stage IQ→IQ→demod decimation pipeline chosen specifically because it recovers ~14 dB of sensitivity versus demodulating early — that ordering lesson (filter and decimate in the complex domain *before* demodulating) is worth internalizing.

Outside Rust, **RTLSDR-Airband** is the canonical scanner-recorder to study. It runs either multichannel mode (demodulating many channels in parallel within one dongle's bandwidth) or scan mode (frequency hopping like an analog scanner), estimates the noise floor per channel to set squelch automatically, and can record to files that rotate on squelch activity so each transmission lands in its own timestamped file — it can even save downconverted narrowband IQ for later processing. And **ham2mon** (GNU Radio/Python) shows the channelizer pattern: it computes an FFT power spectrum probed at ~10 Hz to detect active channels, then spawns parallel demodulators — each a frequency-translating FIR filter plus decimating FIRs down to 12.5 kHz channel bandwidth, a non-blocking power squelch, then quadrature FM demod.

## Architecture

The pipeline that falls out of all this research looks like the diagram below. One wideband IQ stream fans into two consumers: a cheap FFT power monitor that drives the scan/squelch logic, and one or more digital downconverters (DDCs) that extract the channel currently locked.You then run this in one of two scan strategies. **Channelized mode** when your targets fit inside 2.4 MHz: tune the center once (e.g., 27.185 MHz covers all of CB; 162.475 covers all NOAA), and detect activity across every channel simultaneously from the FFT bins — this is what ham2mon and rtl_airband's multichannel mode do, and it gives instant "lock" because nothing has to retune. **Hop-scan mode** for spread-out lists (mixing CB with marine, say): retune the dongle through the list and dwell when the squelch opens. Retuning has real cost — rtl_airband's scan mode changes the device center frequency and is hardcoded to about 5 frequencies per second — because each hop needs PLL settling plus a few ms of samples to judge power, so an analog-scanner feel of 10–20 ch/s is roughly the practical ceiling. A nice hybrid: park on the CB band in channelized mode, and hop a second cheap dongle across VHF.

Threading-wise, the pattern every one of these projects converges on: a dedicated USB reader thread pushing IQ into a lock-free ring buffer, a DSP thread consuming it, and control (retune, squelch level, mode) flowing the other way via channels or atomics — exactly the sdrrat design cited above.

## DSP specifics

The per-channel chain, in the order NyxScope's sensitivity lesson dictates (complex-domain first):

1. **DDC**: multiply the wideband stream by `e^{-j2πΔf·n/fs}` to shift the target channel to 0 Hz, then low-pass and decimate. From 2.4 MS/s, two stages (÷10 then ÷5) get you to 48 kHz with modest filter lengths; the `sdr` crate's FIR/CIC decimators or a hand-rolled polyphase FIR both work. For monitoring many CB channels at once, either run 40 cheap parallel DDCs (fine on a modern CPU at this rate) or graduate to a polyphase filterbank channelizer.
2. **Demod**, dispatched per band: NBFM is the one-liner `arg(x[n] · conj(x[n−1]))` scaled by fs/(2π·deviation), followed by a de-emphasis IIR and a ~3 kHz audio low-pass. AM (CB) is envelope detection — `|x|`, DC-block, AGC. SSB (upper CB channels) is the filter method: shift by ±1.5 kHz, apply a 300–2700 Hz complex bandpass, take the real part, AGC.
3. **Audio**: resample/decimate to 16 or 48 kHz, out to `cpal` and/or the recorder.

## Auto squelch — the interesting part

The consensus design across every mature implementation is *adaptive power squelch with hysteresis*, measured on the channelized complex signal before demod. rtl_airband constantly estimates each channel's noise floor and opens the squelch when signal power exceeds that estimate by a margin (about 10 dB; the default SNR threshold is 9.54 dB) — with the important caveat that floor estimation needs periods of true radio silence, so continuously-transmitting channels like ATIS defeat it and need a manual threshold. That caveat applies directly to NOAA weather channels in your list. NyxScope's refinement is a one-shot calibration at startup plus continuous noise-floor tracking thereafter. The core mechanics beyond the threshold: only update the floor estimate while the squelch is *closed* (slow EMA), open fast (a few ms), and close slowly through a hang time (200–1000 ms) so inter-syllable pauses don't chop the audio. A minimal version:

```rust
struct Squelch { floor_db: f32, margin_db: f32, open: bool, hang: u32, hang_max: u32 }

impl Squelch {
    fn process(&mut self, chunk: &[Complex<f32>]) -> bool {
        let p = chunk.iter().map(|s| s.norm_sqr()).sum::<f32>() / chunk.len() as f32;
        let db = 10.0 * (p + 1e-12).log10();
        let thresh = self.floor_db + self.margin_db;
        if !self.open && db > thresh { self.open = true; self.hang = 0; }
        else if self.open && db < thresh - 3.0 {          // 3 dB hysteresis
            self.hang += 1;
            if self.hang > self.hang_max { self.open = false; }
        } else { self.hang = 0; }
        if !self.open { self.floor_db = 0.995 * self.floor_db + 0.005 * db; } // slow EMA
        self.open
    }
}
```

Two upgrades worth knowing about. A *noise squelch* (what analog FM rigs actually use) measures energy in the 4–8 kHz band of the *demodulated* audio — FM capture means a real carrier quiets that noise, so it discriminates weak-but-real signals from noise bursts better than raw power. And *CTCSS squelch* for repeaters: run a Goertzel detector at the sub-audible tone frequency (67–254 Hz) on the demod output and require it alongside the power gate — rtl_airband supports exactly this, opening squelch only when the configured tone is present, per channel or per scanned frequency.

## Lock, record, resume

The scanner is a small state machine: Scanning → (power over threshold) → Locked, where you dwell, play audio, and record → (squelch closes) → Hang for N ms in case they key up again → resume scanning. Priority channels (CB 9/19, marine 16) get interleaved checks during lock. For recording, `hound` writing 16-bit mono WAV gated by squelch state, with timestamped filenames — rtl_airband triggers file rotation on squelch activity so every transmission becomes its own file, which is exactly the behavior you want. One trick from the field: keep a 1–2 s ring buffer of audio (or IQ) always running so each recording includes the moment *before* the squelch tripped — the same pre-capture idea appears in recent scanner software whose IQ recorder saves the seconds prior to hitting record. If you also dump raw channel IQ for later re-demodulation, pair each file with a SigMF-style JSON sidecar (center freq, rate, timestamps).

One brief legal note since recording is involved: in the US, receive-only monitoring of CB, amateur, marine, NOAA, and analog unencrypted traffic is lawful, but federal law prohibits intercepting encrypted/telephone traffic and divulging or exploiting intercepted communications, and a few states restrict scanner use in vehicles. Receiving at home for your own logging is the safe, normal hobbyist case.

## My recommended stack

For a first build: `rtl-sdr-rs` or `librtlsdr-rs` (pure Rust, no SoapySDR install pain) + `rustfft` + `num-complex` + hand-rolled DDC/demod (genuinely ~400–600 lines) + `hound` + `cpal`, structured as reader-thread → ring → DSP-thread. I'd skip FutureSDR for v1 given its own clone-don't-depend guidance and the recent runtime churn, though sdrrat proves it works well if you want the flowgraph style; `rustradio` is the middle path if you want prefab blocks as a normal dependency. Build order that keeps every step testable: (1) stream IQ and print an FFT waterfall, (2) single-channel NBFM to speakers on a NOAA frequency (always-on carrier = easy win, and remember it needs manual squelch), (3) add the adaptive squelch + WAV-per-transmission, (4) add the channelized CB mode with AM demod, (5) hop-scan state machine, CTCSS, and SSB.
